## Approach

### What was checked (2026-11-17)

- `pnpm audit --prod` (pnpm 10.28.0): one moderate advisory, the path above.
- `pnpm why esbuild`: three versions. 0.28.2 (vite, tsx) and 0.25.12 (drizzle-kit itself)
  are patched; only 0.18.20, under `@esbuild-kit/core-utils@3.3.2`, is vulnerable.
- better-auth 1.7.22: `peerDependencies["drizzle-kit"]` is `>=0.31.4 || >=1.0.0-beta.1`,
  with `peerDependenciesMeta` `optional: true`; its `dist` never mentions drizzle-kit. pnpm
  resolves the optional peer to Opanel's devDependency, which is why the audit counts the
  path as production.
- drizzle-kit 0.31.11 (the `latest` tag): depends on `@esbuild-kit/esm-loader ^2.5.5`, but
  `bin.cjs`, `api.js`, `api.mjs` and `index.js` contain no reference to `esbuild-kit`. It
  loads TypeScript config through `tsx` and its own esbuild 0.25.
- `@esbuild-kit/esm-loader` and `@esbuild-kit/core-utils` are deprecated on npm.
- drizzle-kit `1.0.0-rc.5` depends on `jiti` and esbuild `^0.25.10`, without
  `@esbuild-kit`; it is a release candidate.

### The change

1. **A scoped pnpm override** in `package.json`:

   ```json
   "pnpm": {
     "overrides": {
       "@esbuild-kit/core-utils>esbuild": "0.25.12"
     }
   }
   ```

   It replaces esbuild only where `@esbuild-kit/core-utils` asks for it, and with the
   version the lockfile already holds for drizzle-kit, so nothing new is downloaded. No
   package in `dependencies` or `devDependencies` changes. Then
   `pnpm install` updates `pnpm-lock.yaml`. The selector syntax and the field's place are
   checked against the pnpm 10.28 documentation before writing it (hard rule 13).

   The code that would run this esbuild is never loaded (see above), so the change in
   esbuild's API between 0.18 and 0.25 cannot break anything at run time. The test plan
   still runs every path that uses drizzle-kit.

2. **A dependency audit workflow**, `.github/workflows/audit.yml`: on a weekly schedule,
   on `workflow_dispatch`, and on pull requests that change `package.json` or
   `pnpm-lock.yaml`. It checks out, installs pnpm and Node.js with the same SHA-pinned
   actions as `ci.yml`, runs `pnpm install --frozen-lockfile` and `pnpm audit --prod`.
   It is a separate workflow so that an advisory published tomorrow does not turn every
   unrelated pull request red (question 3). `permissions: contents: read`.

3. **A short note** in `CONTRIBUTING.md`: what to do when the audit fails (look at the
   path and exposure, prefer an upgrade, else a scoped override with a reason in a
   work-spec; never a blanket ignore).

### Considered and not chosen

- **Upgrade drizzle-kit to 1.0 rc**: removes `@esbuild-kit` properly, but it is a
  pre-release with a new config loader, and drizzle-kit 1.0 pairs with drizzle-orm 1.0.
  Too large and too early for a moderate, unreachable advisory (question 2).
- **Ignore the advisory** (`pnpm.auditConfig.ignoreGhsas`): records the decision but keeps
  the vulnerable code installed, and is easy to forget. Not chosen.
- **Override esbuild everywhere** (`"esbuild": "..."`): would also move vite's and tsx's
  esbuild. The scoped selector touches only the vulnerable path.

## Risks and open questions

For the owner:

1. **A scoped override rather than an ignore.** It removes the vulnerable code instead of
   hiding the report, and changes no package Opanel chose. **Recommend: the override.**
2. **drizzle-kit 1.0.** Once it is stable, upgrading removes `@esbuild-kit` and the reason
   for the override. **Recommend: add a follow-up "upgrade drizzle-kit to 1.0 when
   stable, then delete the override" to `docs/README.md`.**
3. **Where the audit runs.** In the main CI workflow it would fail unrelated pull requests
   whenever any new advisory appears; in its own workflow it reports weekly and on
   dependency changes. **Recommend: its own workflow.**
4. **Failure level.** `pnpm audit --prod` fails on any severity, including `low`.
   **Recommend: keep the default (any), since the tree is clean after this item; lower it
   only with a work-spec.**
5. **The branch is stacked on WI-052**, only for the docs index. **Recommend: as
   proposed.**

## Deviations from the approved spec

1. **The override is in `pnpm-workspace.yaml`, not in `package.json`.** The pnpm 10
   documentation (`pnpm.io/10.x/settings`) describes `overrides`, and the `parent>child`
   selector, only in `pnpm-workspace.yaml` at the project root; it does not document the
   `pnpm` field of `package.json`. So `package.json` is not changed at all, and the new
   file holds only the override and its comment. pnpm reads it: a frozen install refused
   the old lockfile until it was updated (`ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`). The audit
   workflow also triggers on changes to that file.
