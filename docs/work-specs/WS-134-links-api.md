## Approach

### 1. Starting point, checked against `main` (`422753b`)

- `task_links` (`src/server/db/schema/task-links.ts`): `from_task_id`, `to_task_id`,
  `type`, `created_by`, `created_at`; primary key `(from_task_id, to_task_id, type)`;
  `task_links_type_check` allows only `regression_of`; `task_links_not_self_check`
  refuses a self-link; an index on `to_task_id`. Both task columns reference `tasks` with
  `on delete restrict`; tasks are only soft-deleted.
- Only `fileBugReport` (`src/server/services/bug-reports.ts`) writes it: one insert, from
  the new bug to the closed one, with no history entry, no version bump and no event for
  the closed task.
- `TASK_LINK_TYPES` (`["regression_of"]`) lives in `src/lib/schemas/bug-reports.ts`;
  `taskLinkSchema` (`{ type, direction, task: { id, key, title } }`, id `TaskLink`) in
  `src/lib/schemas/tasks.ts`, its `direction` described for `regression_of` only.
- `loadLinks(executor, taskId)` and `withLinks(executor, row)` in
  `src/server/services/tasks.ts` read both directions, leave out deleted tasks, and order
  by type, direction (outgoing first) and number. They take no actor: a restricted agent
  sees a linked task outside its projects (WT-09 starting point). `withLinks` is called by
  `getTask`, `updateTask`, `moveTask`, `restoreTask` and each `versionConflict` body.
- `task_events_type_check` allows `created`, `field_changed`, `moved`, `deleted`,
  `restored`, `commented`, `reported_again`. `TaskEventType` in `task-events.ts`,
  `ACTIVITY_EVENT_TYPES` in `src/lib/schemas/activity.ts` and the `what()` switch of
  `src/components/task/activity-text.tsx` list them; the switch is exhaustive, so a new
  type fails the typecheck until it has a sentence.
- `bug-section.tsx` shows every link of `task.links` under "Regression of" or
  "Regressed by" by direction alone: a `blocks` link would read as a regression.
- The task page and the board apply the version rule (WT-04 decision 4, `live.ts`): a
  `task.updated` whose `version` is not newer than the one held is ignored.
- `deleteLabel` (WS-107 section 6) is the precedent for a write that bumps other tasks'
  versions, each with a history entry and a `task.updated`.
- `lockWritableProject` refuses a project the actor cannot reach (`403`) and an archived
  one (`409 project_archived`). Error codes in use include `too_many_labels`; there is no
  `link_exists` or `too_many_links`. The latest migration is `0023_task_updated_index`.

### 2. The data model

One migration, generated by `pnpm db:generate` from the schema changes:

- `task_links_type_check` allows `blocks`, `duplicates`, `regression_of` and
  `relates_to`.
- A new `task_links_relates_to_order_check`, in SQL
  `type <> 'relates_to' or from_task_id < to_task_id` (uuid order), so `relates_to` can
  only be stored once, from the lower id (decision 6). No row breaks it today: only `regression_of` exists.
- `task_events_type_check` gains `linked` and `unlinked`.

No new index: the primary key leads with `from_task_id` and the existing index covers
`to_task_id`, the two sides `loadLinks` and the limit count read.

Item A adds its own migration (`parent_task_id`). Both would be `0024`: whichever merges
second deletes its migration and snapshot, takes in `main`, and runs `pnpm db:generate`
again (`AGENTS.md` section 8).

### 3. The schemas

A new `src/lib/schemas/task-links.ts`:

- `TASK_LINK_TYPES = ["blocks", "duplicates", "regression_of", "relates_to"]`, moved here
  from `bug-reports.ts`, which imports it.
- `taskLinkSchema`, moved here from `tasks.ts` (same id `TaskLink`, same shape), its
  `direction` described for every type with doc 0003's reverse readings: `outgoing` reads
  "this task blocks / duplicates / is a regression of / relates to the other";
  `incoming` reads "is blocked by / is duplicated by / has regression"; `relates_to` is
  always `outgoing`. `tasks.ts` imports it for `taskSchema.links`, whose description
  gains "and that the caller may reach".
- `taskLinkRequestSchema`: `{ type, direction, taskId }`, strict, id `TaskLinkRequest`;
  `taskId` is the other task's id or key, as the path takes (question 3). For
  `relates_to` either direction is accepted and means the same.
- `taskLinkQuerySchema`: the same three fields as query parameters, for `DELETE`.
- `MAX_TASK_LINKS = 100` (decision 3).
- `addTaskLinkContract` and `removeTaskLinkContract`, registered in
  `src/lib/openapi/contracts.ts` (section 8).

### 4. The links service

A new `src/server/services/task-links.ts` owns everything below; `tasks.ts` only calls
`loadLinks` (section 5), and `bug-reports.ts` calls `insertLink` (section 6).

`addTaskLink(actor, ref, input)`:

1. `requirePermission(actor, "tasks:write")` (decision 8, question 3 of WT-09).
2. In one transaction: `findLiveTask(ref)`, else `404`. The other task by
   `input.taskId`, live, else `400` on `taskId` ("There is no such task.", question 4);
   the same task is a `400` on `taskId` ("A task cannot be linked to itself.").
3. `lockWritableProject` for both projects (once when they are the same), in project id
   order so two opposite links cannot deadlock: `403` for a project out of the actor's
   reach, `409 project_archived` for an archived one (question 5). Then both task rows
   `for update`, in task id order.
4. The stored row: `outgoing` stores `(this, other)`, `incoming` `(other, this)`;
   `relates_to` stores `(lower id, higher id)` whatever the direction.
5. The row exists: `409 link_exists`. Either task already holds `MAX_TASK_LINKS` links to
   live tasks, both directions counted: `409 too_many_links`, its detail naming the task.
6. Insert with `created_by` the actor. A concurrent insert of the same row (a unique
   violation) is answered `409 link_exists` too.
7. Both tasks: `version = version + 1`, `updated_at = now()` (question 1); a `linked`
   entry each (section 7); `task.updated` each, with its own `projectId` and new version
   (decision 10).
8. Answer `200` with the path task as `getTask` answers it (question 2).

`removeTaskLink(actor, ref, query)`: steps 1 to 4 the same; no such row is a `404`
("There is no such link."); delete it; step 7 with `unlinked`; answer nothing (`204`). A
link to a deleted task is hidden and cannot be removed until that task is restored (step
2 answers `400`); it stays in the table so restoring brings it back (WS-090).

Reverse links are allowed: `A blocks B` and `B blocks A` may both exist, and so may two
types between one pair. Links are informational and WT-09 adds no graph rules (question
6).

### 5. The answer's `links`: reach (decision 8)

`loadLinks` moves to `task-links.ts` and takes the actor: `join projects p ...
${reachableBy(actor)}` leaves out a linked task in a project the actor cannot reach, as
lists do (WT-05). `relates_to` is answered `outgoing` on both tasks: the incoming branch
of the union maps it to `outgoing`. Order unchanged. `withLinks(executor, actor, row)`
passes the actor at each call site in `tasks.ts`.

**A change to an existing answer:** a restricted agent's `GET /tasks/{taskId}` (and every
other answer that is a `Task`) no longer lists a link to a task outside its projects. The
agent could not read that task anyway (`403`), so it showed only a key and a title the
agent was not meant to see; no client relies on it. Humans and unrestricted agents see no
change.

### 6. Triage (decision 9)

`fileBugReport` calls `insertLink` for `regression_of`, from the new bug to the closed
one, with `{ limit: false }`: the same helper as section 4 steps 6 and 7, without the
limit (question 7): a report is never refused (doc 0001 section 6). The closed task
gets a `linked` entry, a new `version` and a `task.updated`; the new bug gets a `linked`
entry after its `created` entry, and its `task.created` already tells readers (its
version stays 1). Both in the agent's name. Projects are the same, so the bug's project
lock covers both.

### 7. History and activity

`TaskEventType` gains `linked` and `unlinked`. Each entry is written on both tasks, with
`field: null` and the link as that task reads it in `newValue` (`linked`) or `oldValue`
(`unlinked`): `{ type, direction, task: { id, key } }`, `task` being the other one.

`GET /tasks/{taskId}/activity` (`src/server/services/activity.ts` and its schema): `ACTIVITY_EVENT_TYPES`
gains both; the value is answered as stored, except that `task` is `null` when the caller
cannot reach that task's project (question 8), read in the one query per page that WS-117
section 3 already uses for named values. The schema's description names the shape.

The timeline (`activity-text.tsx`): "linked this task: blocks OPA-3" and "removed the link:
is blocked by OPA-3", the reading from doc 0003's table by type and direction, "a task in
another project" when `task` is `null`. The key links to the task, as the bug section
does.

### 8. The routes and contracts

`src/app/api/v1/tasks/[taskId]/links/route.ts`: `POST` reads the body with
`taskLinkRequestSchema` and calls `addTaskLink`; `DELETE` reads the query with
`taskLinkQuerySchema` and calls `removeTaskLink`. No other logic (`AGENTS.md` section 3).

### 9. The bug section

Until item D gives every task a "Links" section (WT-09 decision 12), `bug-section.tsx`
shows only `regression_of` links, so no other type reads as a regression, and appears for
a task with no reports only when it has one.

## API contract

`POST /api/v1/tasks/{taskId}/links` — `tasks:write`, and access to both tasks' projects.

```jsonc
// request
{ "type": "blocks", "direction": "outgoing", "taskId": "API-7" } // id or key
```

| Status | When                                                                              |
| ------ | --------------------------------------------------------------------------------- |
| `200`  | added; the body is the path task (`Task`), its `links` and `version` new          |
| `400`  | invalid body; `taskId` missing, deleted, or the task itself                       |
| `401`  | no credentials                                                                    |
| `403`  | no `tasks:write`, or either task's project out of reach                           |
| `404`  | no live task at `{taskId}`                                                        |
| `409`  | `link_exists`; `too_many_links` (either task at 100); `project_archived` (either) |

`DELETE /api/v1/tasks/{taskId}/links?type=blocks&direction=outgoing&taskId=API-7` — the
same permission.

| Status | When                                                                  |
| ------ | --------------------------------------------------------------------- |
| `204`  | removed                                                               |
| `400`  | invalid query; `taskId` missing, deleted, or the task itself          |
| `401`  | no credentials                                                        |
| `403`  | as for `POST`                                                         |
| `404`  | no live task at `{taskId}`, or no such link (`not_found`, its detail) |
| `409`  | `project_archived` (either)                                           |

Changed answers: `TaskLink.type` gains three values; `Task.links` leaves out tasks
outside the caller's projects (section 5); `TaskActivityEvent.type` gains `linked` and
`unlinked`. All additive for humans and unrestricted agents; no new API version (doc 0004
section 8: no tagged release).

## Risks and open questions

Questions for the owner, each with a recommendation:

1. **Does a link change the tasks' `version`?** The page and the board ignore a
   `task.updated` that is not newer (WT-04 decision 4), so without a bump decision 10's
   events reach no one; but a bump gives someone editing either task a version conflict
   on save, as a label deletion does today. **Recommend: bump both, with `updated_at`,**
   as `deleteLabel` does; the alternative is events without a bump, which needs a change
   to the version rule.
2. **What `POST` answers.** **Recommend: `200` with the path task,** as doc 0004 section 6
   answers a `POST` that acts on an existing resource (adding a team member), so a page
   gets the new links and version in one call. The alternative is `201` with the
   `TaskLink`.
3. **`taskId` in the body.** **Recommend: an id or a key, as the path takes,** so an
   agent can write `API-7`.
4. **A missing other task.** **Recommend: `400` on `taskId`,** keeping `404` for the task
   in the path, as other body references (a team, an epic) are answered.
5. **Archived projects.** A link changes both tasks' history and version. **Recommend:
   refuse adding and removing when either project is archived**
   (`409 project_archived`), as any edit of their tasks is refused.
6. **Reverse links.** **Recommend: allow `A blocks B` beside `B blocks A`,** and two types
   on one pair: links are informational and WT-09 adds no graph rules. The alternative
   refuses the exact reverse of `blocks`, `duplicates` and `regression_of`.
7. **Triage and the limit.** **Recommend: triage's link is never refused,** since a report
   never is; one closed bug gaining 100 regressions is not a real case. The alternative is
   to skip the link past the limit.
8. **Activity naming a task out of reach.** **Recommend: keep the entry, with
   `task: null`,** so the history stays complete without naming the task; the alternative
   leaves the entry out for that caller.
9. **Canonical updates.** **Recommend: this item applies section 10's two amendments,**
   since they describe its behaviour; the alternative leaves them to item F.

Risks:

- **Item A edits the same files** (`tasks.ts`, `schemas/tasks.ts`, the migrations). B keeps
  its logic in `task-links.ts`; its changes to `tasks.ts` are the `withLinks` call sites
  and the moved schema. Whichever merges second rebases, regenerates its migration and the
  OpenAPI document, and reruns the gate (`AGENTS.md` section 8).
- **The answer change for restricted agents** (section 5) is recorded here and in the
  contract's description; it hides only what the agent could not open.
- **A triage regression now bumps the closed bug's version:** someone editing that bug at
  that moment gets a version conflict on save (question 1).
- **Two writes per link** (history and version on both tasks): links are rare next to
  edits.

## Deviations

1. **`TASK_LINK_TYPES` and `taskLinkSchema` did not move** to `src/lib/schemas/task-links.ts`
   (section 3): that file imports `taskRefSchema` and `taskSchema` from `tasks.ts`, so
   moving them would make an import cycle. They stay in `bug-reports.ts` and `tasks.ts`,
   widened and described there.
2. **`loadLinks` stayed in `tasks.ts`** (sections 4 and 5), gaining the actor, for the same
   reason: `task-links.ts` imports `answerTask` and `matchesTask`, newly exported from
   `tasks.ts`, and `tasks.ts` imports nothing from it.
3. **No unique-violation mapping** (section 4 step 6): both task rows are locked
   `for update` before the existence check, so two identical requests run one after the
   other and the second sees the row; test 5 covers it.
4. **Test 10's triage case is in `task-links.integration.test.ts`**, beside WS-090's link
   tests, not in `triage.integration.test.ts`; **test 16 is in `task-detail.test.tsx`**,
   where the bug section's tests already are, not in a new file.
5. **Test 15 was written with the route** in one step, so it was not seen failing on its
   own; the contracts it serves had failed `routes.test.ts` (test 17) until then.
6. **The path task's reach is checked before the other task is looked at** (section 4
   step 2): a caller outside the path task's project gets `403`, never a `400` about the
   other task. The WS-073 coverage test lists `addTaskLink` and `removeTaskLink` as
   project-scoped and `insertLink`, `answerTask` and `matchesTask` as internal.
7. **Doc 0004 section 4's table of codes gains `link_exists` and `too_many_links`**, which
   `scripts/api-conventions.test.ts` requires; section 10 did not list it.
8. **Test 8 has a 30-second timeout**: it creates 100 tasks, which took more than the
   default 5 seconds under the full suite's load.
